# R1：阶段表示的显存、权重存储与部署收益

采用Qwen原主表同一Run048 arena/Graph实验，B8/S2048/O64、固定6 GiB BF16 KV；内存与延迟来自相同策略的三轮测量。与047混合调度双表示常驻及053扩容引擎分开引用。本次只重算历史数据，没有新GPU实验。

| 方法 | GPU峰值 GiB（Torch分配） | GPU Linear权重 GiB | Host阶段权重缓存 GiB | E2E ×BF16 | 完整cycle ×BF16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BF16 | 23.04 | 12.94 | 0.00 | 1.000 | 1.000 |
| SmoothQuant INT8 | 17.64 | 6.48 | 0.00 | 1.661 | 1.661 |
| DASO（均衡） | 15.55 | 5.00 | 8.24 | 2.017 | 1.844 |
| DASO（速度优先） | 16.27 | 5.12 | 8.76 | 2.032 | 1.842 |

GPU峰值取初始化峰值与初始化后重置统计得到的测量峰值之较大者，再取三轮中位数；测量进程包含O1诊断/O64、预热、正式计时和权重核验。它是Torch分配峰值，不包括全部非Torch CUDA/驱动分配。GPU Linear权重是该峰值内的存储子项，不能相加。
Host列仅为持久阶段adapter权重缓存，BF16的0表示没有这项额外缓存，并非CPU总内存为零；它也不是checkpoint磁盘体积。Host与GPU属于不同资源，不能相加成GPU占用。

## 中文回复草稿

感谢审稿人关注阶段异构表示的存储成本。不同阶段使用不同压缩表示确实需要额外的表示存储和生命周期管理。我们的实现对相同阶段表示共享权重，对不同表示使用按层复用的GPU arena，并在CPU端缓存可切换的阶段权重。因此，额外存储并不等同于两份完整模型在GPU上同时常驻，但CPU阶段缓存是一项持续成本，不能仅解释为短暂的峰值。

上表对应原主表的同一执行路径。在固定6 GiB KV cache下，Qwen3-8B均衡/速度优先点的Torch峰值分别为15.55/16.27 GiB，低于BF16的23.04 GiB，分别减少约32.5%/29.4%；相应GPU Linear权重存储为5.00/5.12 GiB，另需8.24/8.76 GiB的CPU阶段权重缓存。这些是代表配置的测量，不意味着全部策略或执行模式具有相同内存收益。

在延迟方面，vLLM集成使用独立copy stream和事件依赖，在某层完成Prefill后准备该层Decode表示，使复制与后续层的Prefill计算重叠。论文Llama-3.1代表点的诊断中，累计复制工作354.94 ms、暴露复制等待1.92 ms；另一次同配置运行时消融中，异步预取将E2E中位数从1625.87 ms降至1521.73 ms（约6.4%，7次配对中5次更快）。这些机制诊断不等于全部传输零成本，也不代替正式E2E。

主表的E2E已包含Prefill到Decode的实际执行与切换；下一批Prefill之前的恢复另计入完整cycle。在同一Qwen实验中，两个DASO点的恢复均值为90.0/102.0 ms；计入恢复后，cycle仍为BF16的约1.844/1.842倍速度。因此可以报告包含该恢复成本后仍有加速，不能声称部署性能普遍不受内存影响。

当前搜索目标是在质量预算下优化延迟，尚未把峰值显存、Host缓存和KV/并发容量作为联合优化约束；运行时已经采用按层复用与预取控制GPU驻留。峰值即使短暂也必须满足设备容量，并会影响可容纳的KV和并发请求。后续可将显存预算纳入搜索，并研究受限预取窗口、分块搬运与buffer生命周期的联合调度，进一步优化内存—延迟折中。这些属于后续方向，不是已验证改进。
